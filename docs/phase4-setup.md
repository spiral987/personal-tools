# Phase 4の起動と使い方

2026-10-31。Recall、Sketchbook、Collectを同じPC・同じ入口で使う構成です。HTTPS公開と実機PWAの確認は後日に行います。

## 起動

Node.js 24以降、pnpm 11.25.0を使います。リポジトリのフォルダーで以下を実行します。

```powershell
pnpm install --frozen-lockfile
pnpm dev
```

- Recall：<http://127.0.0.1:3100/recall/>
- Sketchbook：<http://127.0.0.1:3100/sketchbook/>
- Collect：<http://127.0.0.1:3100/collect/>

3100番が共通の入口です。本体の3102番（Recall）、3101番（Sketchbook）、3103番（Collect）を直接開くと、別originの端末内保存領域になります。普段は3100番から開いてください。`localhost` と `127.0.0.1` も別の保存領域です。

`pnpm dev` は3アプリとgatewayを起動します。Ctrl+Cで自身が起動したプロセスを止めます。1アプリが停止しても残りは動き、停止中のアプリだけ503を返します。個別に作業するときは4つのターミナルで `pnpm dev:gateway`、`pnpm dev:recall`、`pnpm dev:sketchbook`、`pnpm dev:collect` を使えます。個別コマンドは既定の本体ポートを使います。

既存の起動環境と分ける場合は、まとめて起動するヘルパーの入口を指定します。以下では入口3400番、本体3402／3401／3403番になります。

```powershell
$env:GATEWAY_PORT = '3400'
pnpm dev
```

入口は `GATEWAY_PORT`（旧名 `RECALL_PORT` も可）、本体は `RECALL_BACKEND_PORT`、`SKETCHBOOK_PORT`、`COLLECT_PORT` で指定できます。4ポートは別々である必要があります。`SKETCHBOOK_ORIGIN` と `COLLECT_ORIGIN` は任意のNext rewrites用のサーバー設定です。通常のヘルパーは本体ポートに合わせて設定します。既存の環境変数を指定している場合は新しいポートと整合させてください。

本番モードでは開発サーバーを止めてから以下を実行します。

```powershell
pnpm build
pnpm start
```

## アップデート

全アプリの古いタブとインストール済みPWAをいったん閉じ、更新後にオンラインで開き直します。共通IndexedDBをv4へ更新し、既存メモ・スケッチ・スペース・下書き・送信待ちを引き継ぎます。ブラウザの保存データを消す必要はありません。古い画面のまま使い続けず、まず新しい画面へ更新してください。

公開app shellのオフライン準備は本番モードで行います。「保存とアカウント」で準備状態を確認します。3つのmanifest・静的assets・service workerのscopeはそれぞれ `/recall/`、`/sketchbook/`、`/collect/` に閉じています。ログイン情報、API応答、画像の原本はservice workerのキャッシュへ入れません。原本はIndexedDBと非公開Storageに保存します。

## Collectで残す

1. 「URL」でページのURLを貼り、タイトル、出典、自分のメモを添えて保存します。保存済みのURLからページ情報の取得を別の処理で試みます。失敗してもURLとメモは残り、「再試行」やタイトルの手入力ができます。
2. 「画像」でPNG／JPEG／GIF／WebPを選択するかドロップします。1件20MBまで。出典URLやメモと一緒に、変換していない原本を保存します。元画像の書き出しもできます。
3. まず未整理の収集箱へ入れ、スペース、種類、検索、お気に入りで見つけます。同じURLや同じ画像の候補は提示しますが、追加保存もできます。
4. ごみ箱へ移しても復元できます。原本を自動で物理削除する操作はありません。

Web Share Targetに対応するインストール済みブラウザでは、共有メニューからURL・タイトル・テキストを受け取れます。既存の入力を残したまま「下書きに追加」を選び、最後に自分で保存します。共有リンクを開いただけでは保存・外部取得はしません。非対応の環境ではURL貼り付けと画像選択を使います。画像ファイルのShare Target受け取りには対応していません。

## ページ情報の取得

取得対象は公開DNS名のHTTPS・443番に限ります。IPの直接指定、localhost、private／予約済みアドレス、認証情報付きURLは拒否します。DNSの全回答と転送先を毎回検査し、検査したIPへ接続しながら証明書は元のホスト名で確認します。最大3回の転送、全体8秒、HTML本文256KB、入力16KBで打ち切ります。

外部へブラウザのCookieや認証情報は送りません。タイトルと説明は文字列として読み取り、ページのスクリプトや埋め込み画像を実行・取得しません。入力は同じoriginのCollect画面から受け付け、同時4件・1プロセスあたり毎分24件に制限します。これはローカル用途の上限です。将来公開する場合は配置環境のアクセス制御と取得先への外向き通信制限も設定してください。

HTTPのURLも収集自体はできますが、自動取得はしません。ログイン必須のページ、SNS、YouTubeなどは情報取得に失敗する場合があります。SNS本文、字幕、動画本体やAI解析は対象外です。

## 共通ログインと原本の同期

3アプリの `.env.local` に同じ2つの公開設定を置きます。値は既存の接続設定からコピーし、秘密鍵は使いません。

```text
NEXT_PUBLIC_SUPABASE_URL=プロジェクトのURL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=publishable key
```

メールリンク認証とSupabaseの接続は [Phase 2の手順](phase2-setup.md) を参照してください。Collectからメールを送った場合も `/recall/auth/callback/` を使います。リンクは送信した同じブラウザ・originで開きます。同じ入口ではアカウントとCookieを共有し、このブラウザからのログアウトは開いている全アプリへ伝わります。他端末はログアウトしません。

端末内モードの収集は自動でアカウントへ移しません。「端末内の収集を取り込む」で件数を確認してコピーします。元の収集は残り、繰り返すと別IDで追加されます。

収集の記録と画像の原本は別々に同期します。「記録は同期済み」と原本の送信状態を区別してください。原本の転送失敗時は再試行でき、ほかの端末の画像はカードを開いて読み込みます。Storageは既存の非公開 `personal-tools-private` bucketを使い、所有者・収集ID・SHA256で原本の置き場所を分けます。

新しい開発用Supabaseには `supabase/migrations/` のSQLを順番に適用します。既存projectでは適用済みの履歴を確認し、未適用の `20261031011207_phase4_collect.sql` だけを追加します。過去の管理API側の履歴時刻とファイル名が異なるため、確認なしにCLIで一括push・履歴修復をしないでください。今回の実際の反映状況は [検証記録](phase4-verification.md) に記録します。

## バックアップと公開

CollectのJSONには、現在の保存先の収集、ごみ箱、スペース、原本の画像を含みます。下書きは含みません。原本が端末にない場合は取得してから書き出します。画像の合計は1回32MB、読み込むJSONは64MBまでです。大きい場合はカード単位で分けて書き出してください。読み込みは新しいIDで追加します。

RecallとSketchbookのバックアップ形式はそれぞれ従来の範囲を保ちます。Collectの画像を含めた保存データはブラウザの削除や容量回収で失われるため、同期とは別にバックアップを残してください。

HTTPS公開時は [Caddyの例](../deploy/Caddyfile.example) のように、3つの本体へprefixを残して転送します。ローカルgatewayは127.0.0.1専用です。公開domain、SupabaseのSite URL・正確なcallback URL、公開envを設定します。iPhone／Android実機、共有メニュー、機内モード再起動は公開後に確認します。
