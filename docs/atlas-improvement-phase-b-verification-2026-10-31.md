# Atlas改善・段階Bの実装と検証

2026-10-31（日本時間）。[改善計画](atlas-improvement-plan-2026-10-31.md)の段階Bを実装した記録。

## 画面と入口

Recall、Collect、Sketchbook、Atlasを `packages/ui` の共通画面枠へ移した。Recallの色、文字、244pxのサイドバー、79pxのヘッダー、本文幅、余白を基準にした。次の部品を4ツール自身が共用する。

- 画面枠と現在のツール表示
- PCのツール一覧とスペース一覧
- スマホでスクロール後も表示されるツール切替、一覧・スペースの選択
- 見出しの右側に置く検索（スマホでは見出しの下）
- 一覧の見出し・件数・カードグリッド
- 保存状態、設定入口、設定や編集に使うモーダル
- 共通ヘッダーの手動ロック。以前の固定ボタンがスマホの保存ボタンを覆わないよう移動した

各アプリ固有のCSSは本文領域へ限定し、CSSの `app` レイヤーへ移した。共通部品には `pt-` 接頭辞と共有スタイルを使い、アプリごとのナビゲーション、文字、ボタン、メディアクエリが共通領域を上書きしないようにした。描画キャンバス、画像入力、記録の詳細、各バックアップの内容は、共通枠の内側に残している。Sketchbookの保存済み一覧も本文の共通グリッドへ移した。

ローカルgatewayとCaddyの公開用設定例の `/` は `/atlas/` へ転送する。gatewayではルートに付いたクエリも保つ。AtlasホームにはRecall・Collect・Sketchbookへの3つの入口と、既存の横断検索・プロジェクト・原本へのリンクを配置した。各ツールの既存URLと原本IDは変更していない。公開サーバーへのデプロイは段階Cに残っている。

## 下書きを失わない移動

ツールの入口、共通ツール一覧、関連記録、原本へのリンクは、同じ移動処理を使う。通常の同一タブの移動では、次の順番で処理する。

1. 現在の入力と保存先を取得する。
2. メモと編集下書き、画像と下書き、または描画下書きの保存完了を待つ。
3. 保存先が同じままであることを確認する。
4. 次のツールへ移動する。

保存待ち中は二重の移動と入力を止める。保存失敗、保存先の無効化、描画中、ほかの保存処理中は移動しない。失敗時は入力を残してエラーを表示し、再試行できる。ページ内のアンカーとCtrl／⌘などを伴うリンク操作は、通常のブラウザ操作を維持する。

Sketchbookでは、未保存の関連メモIDも暗号化した端末下書きに保持する。関連メモだけが未保存の場合も、別の原本リンクより下書きの復元を優先する。既存の下書きは追加項目なしで読み込める。保存済みスケッチ、同期データ、バックアップの形式は変更していない。

ブラウザ試験はWindowsのBrave（headless、Chromium 156）で、実際のIndexedDB、WebCrypto、Blob、クリップボード、マウス・キーボード入力を使った。通常利用とは別のorigin（`127.0.0.1:3190`）と新しいブラウザコンテキストで、サンプル金庫とサンプル記録だけを使っている。開発版と本番ビルドで確認した。

段階Bの主な確認項目は以下。

- `/` からAtlasホームへの到達、3ツールへの入口。
- 1440px幅と390px幅での各ツールから他の3ツールへの移動（各幅12通り）。現在地表示、検索、設定の到達。
- PCのヘッダー、検索、設定ボタン、スペース見出しの位置・幅・高さが4ツール間で揃うこと。共通の見出しフォント、横にはみ出さないことも確認。
- スクロール後もスマホのツール切替が画面上部に残ること。
- Recallの入力直後に移動しても本文が復元すること。
- 容量エラーを注入すると移動せず、本文を保持し、エラー解消後に再試行できること。
- Collectのタイトル、メモ、画像原本が移動後に復元すること。
- ペンを押している間は移動しないこと。線を確定した後の移動では、線、タイトル、未保存の関連メモが復元すること。
- Atlasの横断検索、プロジェクト作成・絞り込み、既存原本リンクからRecallの該当メモが開くこと。
- スマホ幅の相互移動と、ヘッダーの手動ロック・再解錠でも下書きが残ること。

画面画像8枚（4ツール×PC・スマホ幅）を目視確認した。結果とログは `work/atlas-improvement-phase-b-2026-10-31/` にある。主なファイルは `browser-results.json`、`browser-dev.log`、`browser-production.log`、`tests.log`、`typecheck.log`、`build.log`、`sketchbook-build.log`、`production-http.log`、`suite-*-desktop.png`、`suite-*-mobile.png`。

開始前の作業中変更は保持した。開始時の状態と差分は同ディレクトリの `baseline-status.txt` と `baseline.patch`、4ツールの開始時の画面コードは `*-page.baseline.tsx` に記録した。

## 再実行

段階Aと同じ検証用サーバーを使う。通常の3100番の保存領域を使わず、3191番の4ツールを3190番の検証用入口から開く。

```powershell
$env:GATEWAY_PORT='3191'
node scripts/run-apps.mjs start
```

別のターミナルで次を起動する。

```powershell
node scripts/verify-collect-browser.mjs
```

Playwright CoreとChromium系ブラウザが使える環境で `node scripts/verify-suite-ui.mjs` を実行する。必要なら `PLAYWRIGHT_MODULE` にモジュール指定またはESMのfile URL、`COLLECT_BROWSER_EXECUTABLE` にブラウザ実行ファイルの絶対パスを設定する。通常の `pnpm test` にはPlaywrightのインストールは不要。
